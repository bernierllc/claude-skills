# Tokenizer-first merge guard: one shell tokenizer, decisions on tokens only

Status: planned. Priority: P1. Tracker: https://app.notion.com/p/TOKENIZER-FIRST-MERGE-GUARD-one-shell-tokenizer-decisions-on-tokens-only-claude-skills-plan-owed-41f4efecc95a8185beeffea8ba1d6bf5 (tier and schedule come from the PM task). Owed by PR https://github.com/bernierllc/claude-skills/pull/137 (review-gate 3.2.18), whose "Simplify or plan" section records the raw-text second pass as a stopgap and says "a plan for it is owed". Amends plan `pr-guard-shell-parsing-design.md` (issue #124): its Rule A, Rule B and parity harness become the shared module's, for both guards. Why P1: both guards are the last client-side stop before an unreviewed merge, and each bypass found so far was a real `gh pr merge` that ran while the hook said allow.

## What happened

Two PreToolUse hooks decide, from the Bash command string, whether a command will merge a PR or post a forbidden comment:

- `review-gate/scripts/merge-guard.py` (4,236 lines)
- `pr-merge-flow/scripts/pr-guard.py` (933 lines)

Neither decides on the words the shell will run. merge-guard has dozens of detectors. Some read `shlex` tokens. Some run regexes over raw text (`MERGE_RE`, `_PR_MERGE_LOOSE_RE`, `QUOTE_SMASHED_GH_RE`, `_ARRAY_ASSIGN_RE`, the printf and positional-parameter scanners). Some re-implement one more piece of Bash first (`_dequote_shell_text`, `_collapse_empty_quotes`, `_decode_ansi_c`, the heredoc and comment scanners). pr-guard has its own shlex-based `segments()` with private-use stand-ins for quoted operators.

Each review round found the next spelling that one detector saw differently from Bash:

| PR | Guard | Bypass spellings found in review (each one ran a merge, or would have, while the guard allowed it) |
|---|---|---|
| #129 (pr-merge-flow 1.5.4) | pr-guard | `env -S 'env X=\\c gh pr merge 1 --admin'`: `.split("\\c")` treated an escaped backslash as the start of `\c`. Also `env -S 'gh\c' pr merge 1`, `env '-Sgh\c' pr merge 1`, `env --split-string='gh\_pr\c' merge 1`, `env -S "env X='\c' gh pr merge 1"` |
| #130 (review-gate 3.2.15) | merge-guard | `git commit -m "\"'$(gh pr merge 5 --admin)"\'`: the inert-mention check misread an escaped quote and treated an executed `$(…)` as literal text. `git commit --amend -m "gh pr merge 5 --admin"` with a `post-commit` hook or `GIT_EDITOR` that merges: a blanket `git commit` exemption. #130 fixed both by dropping the inert-mention allowlist: a quoted `gh pr merge` now denies with the `git commit -F <file>` hint (`QuotedMentions`) |
| #132 (pr-merge-flow 1.5.5, open) | pr-guard | `/usr/bin/env -S'gh pr merge 17 --admin'`, `env -vS'gh pr merge 17 --admin'`, `env -S 'env -S "gh pr merge 17 --admin"'`, ``env -S "`printf gh` pr merge 17 --auto"``, `builtin exec env -S 'gh pr merge 17 --admin'`, ``echo `env -S 'gh pr merge 17 --admin'` ``, `bash -c "env -S 'gh pr merge 17 --admin'"` (also `sh -c`, `/bin/bash -c`, `/bin/sh -c`) |
| #137 (review-gate 3.2.18), 3 P1 rounds | merge-guard | `": '" + "z"*16001 + "'; g''h pr mer''ge 7 --squash"` and `g\h pr mer\ge 7` (a size shortcut decided on raw text); `$'\x67\x68' pr $'mer\x67e' 7` and `g\<newline>h pr mer\<newline>ge 7` (Bash finishes the words before running them, the guard did not); `gh pr ` × 2,000 (`MERGE_RE` backtracked past the 25 s hook timeout, and a hook killed at its timeout loses its denial); an 80 KB command took 6-50 s |

#137 ended with this shape:

- `normalize_command` joins continuations and decodes `$'…'` before any check.
- Because that pass does not track quoting, the raw text is checked a second time, and the guard denies if either pass does.
- A 22 s `setitimer` deadline denies before the hook timeout.

The second pass can add a denial but never drops one, so it is safe. But it is a stopgap: every future check now runs twice, on two texts, and still on text instead of words.

## Root cause

Both guards decide on text that Bash has not finished turning into words. Each detector re-derives, its own way, what the shell will run: quoting, escapes, `$'…'`, continuations, wrappers, operators. Two derivations of the same command disagree at the edges, and an attacker (or an unlucky agent) needs only one detector to say "no merge here". The review loop finds one disagreement per round. Nothing makes a fix in one detector reach the others.

## What already exists, and what this plan reuses

Incumbent check: does this reimplement something the framework, a dependency, or this repo already provides?

- **`shlex` (stdlib)** is the base of both guards' tokenizing today (`merge-guard._shell_tokens_once`, `pr-guard.shell_tokens` with `punctuation_chars`). This plan keeps it as the word splitter inside spans the scanner has proven plain (section 1). It does not add a parser dependency. bashlex is unmaintained and has no `$'…'` or `env -S`. tree-sitter-bash is a compiled wheel a hook cannot assume. Both would also re-implement Bash.
- **`pr-guard.segments()`** is the most complete existing tokenizer: operator-aware, with quoted-operator stand-ins, and a fail-closed path when shlex cannot parse. It is the starting point of the shared module, not a second design.
- **`merge-guard.normalize_command` and `_decode_ansi_c`** (3.2.18) already do the pre-word steps. They stay in phase 1. The shared module's scanner takes over the same steps with quoting tracked, and the raw-text second pass goes in phase 2, once the corpus differential covers it (section 0).
- **merge-guard's 3.2.18 denials are the floor.** It denies, among others: `watch`, `find -exec`, `stdbuf`, `ssh`, `docker exec` and `xargs` wrapping a merge; `su -c`, `bash -c`, `eval`; `<(…)`, `${x:-$(…)}`, `$(…)` and backticks anywhere; heredoc bodies; a quoted `gh pr merge` mention in any argument; a dynamic `gh` executable name (`$X pr merge 7`, `'gh\<newline>' pr merge 7`); a dynamic subcommand slot (`gh $X merge 7`, `gh pr $X 7`, `gh $X`); a merge spelled through expansions (`gh${IFS}pr${IFS}merge 7`) or mentioned in a word that also expands (`"gh pr merge $N"`); `gh pr merge` assembled from a function, an array, `set --` or a variable (`a=(gh pr merge 7); "${a[@]}"`, `set -- gh pr merge 7; "$@"`, `c=gh; $c pr merge 7`); `gh`, `pr`, `merge` passed as arguments (`echo gh pr merge 7`); dynamic argv after `gh pr merge` (`gh pr merge $N`); compound commands (`{ …; }`, `( … )`, `if … fi`) and alias invocations that run a merge; a merge with flags between its words (`gh pr -R o/r merge 7`, `gh pr --repo=o/r merge 7`, `gh pr -Ro/r merge 7`, `gh pr -h merge 7`) and with a dynamic `-R` operand (`gh pr -R $REPO merge 7`); `gh`, `pr` and `merge` assembled across variables (`a=gh; b=pr; c=merge; $a $b $c 7`, also through `export`, `+=`, `printf -v` and `${c:1}`); and any hook payload that carries a `command` or `cmd` string, whatever the tool is called (`run_shell_command`, `mcp__x__Bash`). **pr-guard's floor** is a different, smaller set: its flag and check rules on every `gh pr merge` it finds, and its Codex-mention denial, which reads posted text from `--body`, from a heredoc or here-string on stdin (`gh pr comment 5 --body-file - <<'EOF'`, `<<<`, `--body "$(cat <<'EOF' … EOF)"`) and from a file written earlier in the same command (`cat > b.md <<'EOF' … EOF`, then `gh pr comment 5 -F b.md`); it checks `tool_name == "Bash"` only. All of this was verified against `origin/main` f658d1b (review-gate 3.2.20, pr-merge-flow 1.5.4) by running the real hooks: `python3 -I merge-guard.py` and `pr-guard.py` with a JSON payload on stdin, from a directory with no GitHub remote. **Phase 1 keeps every one of these detectors running beside the tokenizer** (section 0): a command is denied when today's detectors deny it or a tokenizer rule does. Phase 2 retires a detector only after the corpus-differential test shows the tokenizer denies everything that detector denied. Every row in the test table below states its result today in each guard; a row the plan denies and that guard allows today is marked **new deny** in that guard's column, and the one known limit both allow is marked as such.
- **Plan `plans/pr-guard-shell-parsing-design.md`** (issue #124) already fixes pr-guard's wrapper rules (Rule A and Rule B) and its regression harness. This plan does not redo that. It takes Rule A and Rule B as the wrapper policy of the shared module, so merge-guard gets them too.
- **`pr-merge-flow/tests/test_pr_guard_parity.py`** (landed in #127, aeae404) is the differential harness: baseline guard from `origin/main` against head, and every block the baseline had must survive. The same harness is extended to merge-guard, and its "every block the baseline had must survive" check is the phase-1 invariant (section 0). It is not rewritten.
- **Deadlines today.** merge-guard has `HOOK_BUDGET_S = 20.0` for `gh` calls plus a `CHECK_DEADLINE_S = 22.0` `setitimer` alarm around the whole check (25 s hook timeout in `review-gate/hooks.json`). pr-guard has `GH_BUDGET_S = 15` and `_left(deadline, cap)` (20 s hook timeout in `pr-merge-flow/hooks.json`) and no alarm. `check-review-gate.gh_deadline` is a third, but it belongs to the CI checker, which is installed standalone and is not a hook; it stays as it is.
- **The byte-identical mirror pattern** (`scripts/check-review-gate.py` ↔ `review-gate/scripts/check-review-gate.py`, pinned by a test) is how one file ships inside two skills that are vendored independently.
- **Plan `docs/superpowers/plans/2026-11-17-api-merge-guard.md`** moves enforcement server-side, so an API, GraphQL or `git push` merge cannot skip the gate. That is the real boundary. This plan makes the client-side hook honest and cheap; it does not replace that plan, and its priority does not depend on it.

## Correct fix

### 0. Phase 1 is additive: today's detectors stay, the tokenizer adds denials

Round 3 of review found four commands that today's guards deny and that a tokens-only design would have allowed. Each was run on `origin/main` f658d1b with the real hooks (rc 2 is deny):

- `gh pr -R o/r merge 7` (flags between `pr` and `merge`): rc 2 in both guards. The first draft's merge words had to be adjacent.
- `a=gh; b=pr; c=merge; $a $b $c 7` (assembled from variables): rc 2 in merge-guard (its variable-assembly detector), rc 0 in pr-guard. No first-draft rule saw it: the command word is `Unresolved` and `merge` is nowhere in it.
- `gh pr merge 7 --admin` with `tool_name` `run_shell_command` (also `mcp__x__Bash` and `execute_command`, and a payload whose command sits under `input` or `cmd`): rc 2 in merge-guard, rc 0 in pr-guard, which checks `Bash` only. A shared `run_hook` that applied one tool-name policy would have turned one guard's rc 2 into rc 0.
- `gh pr comment 5 --body-file - <<'EOF'` with `@codex review` in the body: rc 2 in pr-guard (its Codex-mention denial), rc 0 in merge-guard (it has no comment rule). The first draft exposed quoted-delimiter heredoc bodies and here-strings to no rule.

One cause: the first draft replaced today's detectors with rules written from a list of denials, and nothing proved the rules cover the detectors. "Adds no allow" was a claim, not a property of the design. This section makes it a property:

- **Phase-1 invariant.** For every command C and each guard, `guard_after(C)` denies whenever `guard_before(C)` denied. New denials = (today's detectors, unchanged, in both guards) OR (the tokenizer's rules). A tokenizer rule that misses a spelling cannot turn it into an allow, because the detector that denies it today still runs. The tokenizer can only add denials.
- **Phase 1 deletes no detector.** `normalize_command`, the raw-text second pass, merge-guard's regexes and scanners and pr-guard's `segments()` all stay. Each guard's check runs two functions and denies if either does: `legacy_checks` (today's code, untouched) and `token_checks` (the tokenizer's rules, section 2). They are separate functions so a test can call each alone.
- **The tool-name policy is not shared.** It stays in each guard (section 3).
- **Phase 2 retires legacy detectors one family at a time**, each only when a corpus-differential parity test shows `token_checks` denies every corpus command that family's detectors denied (Tests, "Parity corpus"). A corpus command the tokenizer cannot deny keeps its detector alive; the command is never dropped from the corpus to make the test pass.

Incumbent answer: does this reimplement something the framework, a dependency or this repo already provides? In part, yes, and deliberately: the legacy detectors are the incumbent. Phase 1 keeps them running and adds the tokenizer as a second reader. Phase 2 replaces each one only on evidence that the tokenizer covers it.

### 1. One shared tokenizer: `shell_tokens.py`

One file, shipped as byte-identical copies in `review-gate/scripts/shell_tokens.py` and `pr-merge-flow/scripts/shell_tokens.py`. A repo test fails when the two differ. The skills are vendored separately into other repos, so neither may import the other's directory.

Its one entry point, `shell_tokens.tokenize(cmd) -> Parsed`, is the only function in either guard that reads the command string. `Parsed` holds the **segments**, the **comments** (where the `# review-gate-ok:` and pr-guard overrides live), the **bindings** (each variable name the text assigns, with every `Literal` value it can hold: `n=v`, `n+=v`, `export|declare|local|readonly n=v`, `printf -v n v`; R9 reads them) and a list of **parse failures**. Each segment is a list of **words** plus its **redirects**, and each word is one of:

- `Literal(text)`: a word whose final text is fully known after Bash's quote removal, escapes, `$'…'` decoding and continuation joins, decided per quoting context: a backslash-newline joins only outside single quotes, and `\c`, `\\` and escaped quotes are read in the context they appear. `$'…'` is decoded exactly or not at all: an escape the decoder does not reproduce byte for byte is a parse failure (R7), never a guess, so `$'…'` never needs to be `Unresolved`.
- `Unresolved(reason, raw, nested, fragments, names)`: a word that Bash still changes after tokenization, so its final text (or its number of words) is unknown from the command string. **Every expansion Bash performs after splitting into words makes a word `Unresolved`**, in any position, not only the command position: brace expansion (an unquoted `{a,b}` or `{1..3}`), tilde expansion (an unquoted leading `~` or `~user`, and a `~` after `=` or `:` in an assignment value), parameter and arithmetic expansion (including `${x:-…}` forms), command substitution (`$(…)`, backticks), process substitution (`<(…)`, `>(…)`), and pathname expansion (an unquoted `*` or `?`, a bracket expression `[…]` closed in the same word, and the extglob forms `?(…)`, `*(…)`, `+(…)`, `@(…)`, `!(…)`). The same characters inside quotes are literal, so `'*'`, `"{a,b}"` and `"~"` stay `Literal`. An `Unresolved` word may stand for zero, one or several words; the rules treat it as one unknown slot. The reason names the construct. A substitution has two effects, and the word keeps both: Bash runs the body, and its output becomes part of the word. `nested` carries each body that Bash runs (`$(…)`, backticks, `<(…)`, `>(…)`, and a `$(…)` inside `${x:-…}`), parsed into segments by the same function. `fragments` is the word's known literal text in order, with one hole where each expansion stands, after the same quote removal and escapes as a `Literal` (`gh${IFS}pr${IFS}merge` → `gh`, hole, `pr`, hole, `merge`; `"gh pr merge $N"` → `gh pr merge `, hole; `m{erge,}` → `m`, hole; `mer*` → `mer`, hole; `~/bin/gh` → hole, `/bin/gh`). Decisions may read `fragments`, which come from tokens. `raw` is the source span, used only to write the denial message; no decision reads it. `names` has one entry per hole: the parameter's name when the hole is a parameter expansion (`$a`, `${a}`, `"$a"`, and `${a:1}`, whose modifier is ignored), `None` for any other expansion; R9 reads it.
- `Nested(segments)`: the parsed body of a string that a wrapper hands to a shell as a command, where the word itself is consumed rather than kept as text: `bash|sh|zsh|dash|ksh -c`, `su -c`, `ssh <host> <command…>`, `docker|podman|kubectl exec … sh -c`, `env -S`/`--split-string` (including attached `-S'…'`, short clusters such as `-vS'…'`, and `\c` truncation), `eval`, `watch <command…>`, `find -exec|-execdir|-ok|-okdir … ;`, `xargs`, and a heredoc or here-string body when the segment's command is a shell (`bash <<EOF`, `sh <<< '…'`, quoted delimiter or not), parsed as a whole script.
- `Heredoc(delimiter, quoted, text)`: the body of a heredoc or here-string that is not a shell script (`cat <<'EOF'`, `gh pr comment --body-file - <<EOF`, `cat > b.md <<'EOF'`, `<<< 'text'`), held in the segment's `redirects` beside its operator (`<<`, `<<-`, `<<<`, `>`, `>>`, `<`) and target. `text` is the body after the stripping Bash does (`<<-` tabs, quote removal for a here-string word). With an unquoted delimiter Bash expands the body, so each substitution in it gives the body `nested` bodies, as in an `Unresolved` word, and the rules run on those. No command-position rule reads the text itself. Two rules read it as text: R3, when the body sits inside a `nested` body, so its output becomes part of a word (`git commit -m "$(cat <<'EOF'` … `gh pr merge 7` … `EOF)"`, which merge-guard denies today; a top-level `cat <<'EOF'` body is not read, and both guards allow it today); and R10, pr-guard's posted-text rule, which takes the text a command reads from stdin (`--body-file -`) from the segment's own `Heredoc`, and the text it reads from a named file (`-F b.md`) from the `Heredoc` of an earlier segment in the same command that wrote that literal name (`cat > b.md <<'EOF'`).

Segments split on control operators (`;`, `&&`, `||`, `|`, `|&`, `&`, newline) and keep the operator, so a detector can still ask "does this run after a `cd`". Grouping and reserved words (`{`, `}`, `(`, `)`, `if`, `then`, `elif`, `else`, `fi`, `while`, `until`, `do`, `done`, `case`, `esac`, `function`, `name()`) also start a new segment, so the body of a group, subshell, condition, loop or function definition is its own segment and its first word is a command position. An array assignment `a=(w1 w2 …)` yields its elements as words of the segment, in order.

**Failures are part of the result, never an exception.** An unbalanced quote, an unknown `$'…'` escape, an unterminated `$(`, `${` or heredoc, a nesting depth past the cap, or a time or size budget hit is recorded in `Parsed.failures` with the construct and its offset. Section 2 denies the whole command on any failure.

**How it finds the ends of constructs.** One left-to-right scanner with a stack of quoting contexts (plain, single, double, `$'…'`, `$(…)`, backticks, `${…}`, `<(…)`/`>(…)`, heredoc). It tracks nesting itself and finds where each construct ends, including `)` inside quotes inside `$(…)`, `}` inside `${x:-"}"}`, and heredoc delimiters (with `<<-` tab stripping and quoted delimiters). shlex is never given text with an open construct: it splits only the plain spans between constructs, which the scanner has already closed. Each body found is fed back through `tokenize`, with the depth cap.

**Wrapper policy.** The shared module applies the #124 plan's Rule A and Rule B. Rule A's list (every later word is a candidate command) is at least every wrapper 3.2.18 denies: `env`, `sudo`, `doas`, `su`, `nice`, `ionice`, `timeout`, `xargs`, `nohup`, `time`, `exec`, `builtin`, `command`, `stdbuf`, `setsid`, `chroot`, `watch`, `find -exec` and its siblings, `ssh`, `docker|podman|kubectl exec`. Absolute and relative paths to any of them (`/usr/bin/env`, `./bash`) count.

**Command names match by basename.** Wherever a rule asks what command a word names, it compares the word's text after its last `/`: `/opt/homebrew/bin/gh`, `./gh` and `/usr/bin/gh` name `gh`, and `/usr/bin/env` names `env`. This is one function in `shell_tokens` (`command_name(word)`), used for `gh` and for every wrapper, so no rule compares a full path or a bare name on its own. An `Unresolved` command word has no known name (`~/bin/gh`, `$HOME/bin/gh`, `g{h,}`), so R4 decides it.

Rule B (directory and root are known only after nothing, a plain `command`, or `env NAME=value…`) is unchanged. pr-guard's own copy of these rules is deleted in phase 2, after the corpus differential (section 0), not in phase 1.

The wrapper list is not what finds a merge. Section 2's R2 (both guards) and R3 (merge-guard) look at every word of every segment, so a wrapper missing from the list still denies (as `unknown-wrapper gh pr merge 7` does today); the list only decides which strings are parsed as `Nested` and where Rule B can know the directory.

**Cost.** The scanner is one pass with a stack, linear in the length of the command; shlex on each closed plain span is linear too. Each distinct text is tokenized once (`lru_cache`, as 3.2.18 already does). No regex in the module may backtrack: every pattern is anchored or a fixed literal. A size or depth cap records a failure, which denies. The module has a test that times `gh pr ` × 2,000, 80 KB of padding before a merge, 2,000 nested quotes and 500 nested `$(` against a 1 s budget.

### 2. Decisions on tokens only, fail closed on anything unresolved

At the end state (after phase 2) every detector in both guards takes `Parsed`, never a string; in phase 1 these rules are `token_checks`, which run beside today's detectors and only add denials (section 0). **Decisions read tokens only:** a `Literal`'s text, an `Unresolved` word's `reason` and `fragments`, `Nested` bodies, operators and comments. No rule reads `raw` or the command string, so brace, glob, tilde and `$'…'` spellings reach a rule already resolved into `Literal` or `Unresolved` by section 1, never as text a rule must re-interpret. The rules below reproduce 3.2.18's denials on words. Each is named so the test table and the denial message can cite it. Every rule applies to every segment, to every `Nested` body and to the `nested` bodies of every `Unresolved` word, recursively. A segment's **merge words** are a `Literal` command word whose `command_name` is `gh` (section 1: by basename), then `pr`, then `merge`, as `Literal` words in order. A flag between them is skipped: a `Literal` word starting with `-` is a flag, and `-R`, `--repo` and `--hostname` take the next word as their operand unless the operand is attached (`-Ro/r`, `--repo=o/r`: one word). So `gh pr -R o/r merge 7`, `gh -R o/r pr merge 7`, `gh pr --repo=o/r merge 7` and `gh pr -h merge 7` are all merges. An `Unresolved` word in a flag, operand or subcommand position is R5 or R6, never skipped silently.

**Which rules each guard applies.** The two guards share the tokenizer and the rules that find a merge that runs; they differ in what they do with it.

- **merge-guard** (review-gate) applies R1 to R9, then the gate checks to each top-level R1 merge.
- **pr-guard** (pr-merge-flow) applies R1, R2, R4, R5, R6, R7 and R9, then its own rules (R10 among them) (`--squash`/`--merge`, a literal 40-hex `--match-head-commit`, no `--admin` or `--auto`, green checks, and its draft, polling and comment rules) to every merge R1 finds, wherever R1 finds it: top level, behind a wrapper, in a `Nested` body or in a group. It does not apply R3 or R8. R3 denies text that mentions a merge without running one (a commit message, a grep pattern, a file name), and R8 denies shell-state changes that make a later `gh` untrustworthy; both are review-gate's policy for the review gate, and a repo that carries only pr-merge-flow gets no new mention or state denials from this plan. R2 stays in pr-guard because pr-guard denies an array-assembled merge (`a=(gh pr merge 7); "${a[@]}"`) today. R2 fires only on `gh`, `pr` and `merge` as three consecutive separate `Literal` words, so a commit message or a quoted grep pattern (one word) does not trigger it. An unquoted pattern does: `grep -n gh pr merge SKILL.md` is denied by merge-guard today (probed on f658d1b) and, after this plan, by pr-guard too (**new deny**). The fix for the user is to quote the pattern.

The table under Tests has one column per guard, so "passes where it applies" means each guard's column.

- **R1 executed merge.** The segment's merge words start at a command position: the first word of the segment, or a later word that Rule A makes a candidate command. In merge-guard, only a merge in a top-level segment whose command word is the bare `gh` goes on to the gate checks (reviews, threads, labels), and only behind the wrapper prefixes 3.2.18 gate-checks today. In merge-guard, the same merge words with a path-qualified `gh` (`/opt/homebrew/bin/gh`, `./gh`, `sudo /usr/bin/gh`), at a command position inside a `Nested` body (`bash -c`, `ssh`, `env -S`, …), or inside a group, subshell, condition, loop or function body deny outright as wrapped or compound, as 3.2.18 does ("run `gh -R owner/repo pr merge <n>` directly"); the parity harness pins which is which. pr-guard applies its own rules to every R1 merge (above). A wrapper missing from Rule A's list still reaches R2.
- **R2 displaced merge words.** The segment has merge words as separate `Literal` words, but `gh` is not at a command position: `echo gh pr merge 7`, `printf '%s ' gh pr merge 7`, `set -- gh pr merge 7`, the elements of `a=(gh pr merge 7)`, arguments to a function or to an unlisted wrapper. Deny: "`gh pr merge` must be the directly executed command". This is what denies array, positional and function-argument assembly without evaluating it.
- **R3 mention.** A word's text contains a `gh … pr … merge` spelling (the three words in order, separated by whitespace). For a `Literal` the text is the word; for an `Unresolved` it is its `fragments` joined with each hole read as a word separator. Deny with the hint 3.2.15 added: "write the message to a file and use `git commit -F <file>`". This covers a commit message, a grep pattern, a file name, an assignment value (`x="gh pr merge"`), a mention that also expands (`git commit -m "run gh pr merge $N"`, `echo "gh pr merge $N" | bash`) and a merge spelled through expansions (`gh${IFS}pr${IFS}merge 7`). It keeps the no-inert-mention rule that `QuotedMentions` (`review-gate/tests/test_merge_guard_hyphen.py`) pins: rc 2 plus the `git commit -F` hint. A `Heredoc` body inside a `nested` body is part of its word's text (section 1): `git commit -m "$(cat <<'EOF'` … `run gh pr merge 7` … `EOF)"` denies with the same hint, as today, while a top-level `cat <<'EOF'` body that only reaches `cat` or a file is not a mention, as today. There is no allowlist of "inert" commands or arguments.
- **R4 unresolved command name.** A word at a command position is `Unresolved`, and a later word in the segment is the `Literal` `merge` or one of the command word's own `fragments` is `merge` (`$X pr merge 7`, `c=gh; $c pr merge 7`, `$(printf g)h pr merge 7`, `'gh\<newline>' pr merge 7`, `g{h,} pr merge 7`, `~/bin/gh pr merge 7`, `$HOME/bin/gh pr merge 7`, `gh${IFS}pr${IFS}merge 7`). `$X pr view 7`, `$EDITOR notes.txt` and `gh${IFS}pr${IFS}view 7` stay allowed, as in 3.2.18.
- **R5 unresolved subcommand.** The command name is `gh` and either subcommand slot after the global flags is `Unresolved`, whatever follows (`gh $X merge 7`, `gh pr $X 7`, `gh $X`, and the brace and glob spellings `gh pr {merge,} 7`, `gh pr m{erge,} 7`, `gh pr merg[e] 7`, `gh pr mer* 7`, `gh pr vie* 7`). The operand of `-R`, `--repo` or `--hostname` is not a subcommand slot: `gh pr -R $REPO merge 7` is an R1 merge with an `Unresolved` operand, which R6 denies.
- **R6 dynamic merge argv.** An R1 merge has an `Unresolved` word anywhere in its words after `gh`: after `merge` (`gh pr merge $N`, `f() { gh pr merge "$@"; }; f 5`), or as the operand of `-R`, `--repo` or `--hostname` before it (`gh pr -R $REPO merge 7`, `gh -R $REPO pr merge 7`; both guards deny these today). The guard cannot know the PR, repo or flags, so it denies instead of checking gates on a guess.
- **R7 parse failure.** Any entry in `Parsed.failures` denies the whole command, naming the construct and offset. **Cost:** this denies a few commands that today's guards allow and Bash runs, for example a heredoc with no closing delimiter (`cat <<EOF` newline `hi`: Bash warns and runs it). Both guards allow that today, so these are **new denials**; the fix for the user is to close the construct. An unterminated quote or `$(` (`echo 'unterminated`, `echo $(ls`) is also allowed by both guards today; Bash rejects those as syntax errors, so denying them costs nothing.
- **R8 effects outside the text keep today's detectors, rewritten to read words.** These exist in 3.2.18 and move as they are: `PATH` and other shell-state assignments (including `case … ) PATH=`, `((PATH=0))`, `let`, `unset PATH`), `hash -p`, alias and function definitions of `gh` or of a command that then runs a merge (an alias body is a shell string, parsed as `Nested`, so `alias m='gh pr merge'` then `m 7` denies), and `command_not_found_handle`. They read `Literal("PATH=…")` assignment words and `Literal("alias")` command words instead of regexes over raw text. No new detector is added here; effects the text cannot show are under Not in scope.
- **R9 assembled merge** (both guards). A word at a command position is `Unresolved`, every hole in it is a parameter (`names` has no `None`), and replacing each name with a value from `Parsed.bindings` can make that word and the next two slots spell `gh` (by basename), `pr`, `merge`, with R1's flag skipping: `a=gh; b=pr; c=merge; $a $b $c 7`, the same quoted (`"$a" "$b" "$c"`), through `export a=gh …`, through `c=g; c+=h`, through `printf -v c gh`, and with modifiers (`"${c:1}"`: a modifier is ignored, so R9 denies a spelling that, with the modifier applied, is not a merge; it is as conservative as the detector it mirrors). `bindings` holds every value the text assigns a name in any segment. No control flow is evaluated, so an assignment in either branch of an `if` counts, and a name with several values fires if any combination spells the merge. `a=gh; b=pr; c=merge; echo $a $b $c` (the command is `echo`) and `a=x; b=y; c=z; $a $b $c 7` (the values spell no merge) stay allowed. R9 mirrors merge-guard's `variable_assembled_merge`; pr-guard has no such detector today, so in pr-guard it is a new deny.
- **R10 posted text** (pr-guard only). pr-guard's Codex-mention denial (`codex_mention_post` today) reads the text a posting command (the commands `comment_posts` recognises) sends from its words (`--body`, `-b`, including a quoted heredoc body inside an `Unresolved` word's `nested` body, `--body "$(cat <<'EOF' … EOF)"`), from the stdin `Heredoc` of the segment (`--body-file - <<'EOF'`, `<<<`) and from the `Heredoc` of an earlier segment that wrote the named file (`-F b.md`), instead of scanning raw text. It must deny every comment row in the Tests table before the raw-text version is retired.

Each denial names the rule and, for R4 to R6 and R9, the construct from `Unresolved.reason`: "the command name comes from `$X`; write it literally".

**Known limit, unchanged from 3.2.18: a command name computed at run time.** `$(printf 'gh pr m%s' erge) 7` and `x=$(printf 'gh pr m%s' erge); $x 7` are allowed today, and the plan keeps allowing them. No word is `merge` and no fragment spells it, so R3 and R4 do not fire. A rule that denied them (any `Unresolved` command word followed by any argument) would also deny `$EDITOR notes.txt` and every `"$cmd" args` script line, and still miss `$(cat cmd.txt)`. The boundary for computed commands is the server-side plan; the test table pins these two as allowed so a later change has to say so if it moves them.
- **The raw-text second pass and `normalize_command` are deleted in phase 2,** once the corpus differential shows the tokenizer covers them. They exist only because the first pass lost quoting; phase 1 keeps them.
- **Overrides** (`# review-gate-ok:`, the pr-guard overrides) are read from `Parsed.comments`.

### 3. Fail closed on a crash or a missing module

A hook that exits with anything but 2 lets the command run. Today merge-guard's `__main__` catches `BaseException` and exits 2, but pr-guard's `__main__` logs and re-raises, so a crash exits 1 and the merge runs.

- A second mirrored file, `hook_runtime.py`, ships byte-identical in both skills' `scripts/` (same mirror test). It holds `run_hook(main, alarm_s)`, which both guards' `__main__` call. `main` is the guard's own function from the parsed payload to a verdict (it decides which tool calls it checks, below), and `alarm_s` is section 4's alarm. It catches `BaseException`, prints a denial naming the exception, and exits 2. A `SystemExit` passes through only for codes 0 and 2.
- **Unreadable hook input denies.** pr-guard's `main` returns 0 today when stdin is not JSON (`except ValueError: return 0`); `run_hook` reads stdin itself and denies instead, for both guards. merge-guard already denies it (3.2.20).
- **Which tool calls a guard checks stays in each guard, not in `run_hook`, in phase 1 and after.** Today the two differ, verified on f658d1b. merge-guard checks any payload whose `tool_input` (or `input`) carries a `command` or `cmd` string, whatever the tool is named: `gh pr merge 7 --admin` is rc 2 under `Bash`, `mcp__x__Bash`, `run_shell_command` and `execute_command`, and with the command under `input` or `cmd`; `ls` under `run_shell_command` is rc 0. pr-guard checks `tool_name == "Bash"` and reads `tool_input.command` only, so the same `gh pr merge 7 --admin` under `run_shell_command` is rc 0. A `run_hook` that applied one policy would flip a guard: a Bash-only policy would turn merge-guard's rc 2 into rc 0, the one thing this plan must not do, and the command-key policy would add denials to pr-guard that nobody reviewed. So each guard keeps its own `extract_command(payload)`, and `run_hook` never reads `tool_name` or the input keys. Aligning pr-guard with merge-guard is a separate change (Not in scope).
- **What exit 2 does depends on the agent.** Exit 2 is the deny code for Claude Code `PreToolUse` and Gemini `BeforeTool`. aec translates `hooks.json` per agent: Cursor has no exit-code deny and Codex has no entry for this event, so on those agents neither guard denies, before or after this plan. That is aec's hook-translation surface, not this plan's. The skill `hooks.json` keeps `timeout_ms`; aec writes each agent's own field (Claude Code's `timeout`, in seconds).
- Each guard loads `hook_runtime` and `shell_tokens` from its own directory inside a `try` that is the first statement of `__main__`. An `ImportError` or any error while loading prints "review-gate: guard module missing or broken (`<name>`); reinstall the skill" and exits 2. A test deletes each module from a copy of the skill and asserts rc 2 for a plain `gh pr merge 7` and for `ls`.
- **Rollback.** Each step below is one PR. If a released step blocks real work, revert that PR and release the revert as the next patch. The release before step 2 does not import either module, so a revert back to it is self-contained. A vendored copy missing one of the new files fails closed by the rule above. For review-gate, the whole-copy refresh from 3.2.19 (`install-workflow.py --force`) replaces `.claude/skills/review-gate` as one unit, so a half-updated copy is not a normal state. It does not touch `pr-merge-flow`, which has no installer of its own: its vendored copy is refreshed by `aec install skill pr-merge-flow`, or by replacing the directory with the release's as a whole; a partial copy still fails closed.

### 4. One deadline per hook run

- `hook_runtime.Deadline` is one monotonic deadline set in `run_hook` (the cooperative deadline below), passed to every check and every `gh` call. It replaces merge-guard's `HOOK_BUDGET_S` and `CHECK_DEADLINE_S` and pr-guard's `GH_BUDGET_S` and `_left`.
- Each guard has two numbers, both derived from its own `hooks.json` `timeout_ms`. The **alarm** is the timeout minus a 3 s margin: 22 s for merge-guard (25 s timeout), 17 s for pr-guard (20 s timeout). The **cooperative `Deadline`** is 2 s earlier than the alarm: 20 s and 15 s, which are today's `HOOK_BUDGET_S` and `GH_BUDGET_S`, so cooperative behavior does not change. The alarm is today's `CHECK_DEADLINE_S` for merge-guard and new for pr-guard. The cooperative deadline expires first, so a stuck `gh` call produces the message that names the step; the alarm fires only when a step cannot reach a `Deadline.check()`. A test reads each skill's `hooks.json` and fails when `alarm_s + 3 > timeout_ms / 1000` or `deadline_s + 2 > alarm_s`, so a timeout change cannot leave either number past its limit.
- **The margin is measured, not assumed.** The margin has to cover what runs outside the deadline: interpreter start, imports, reading stdin, and printing the denial after expiry. 3 s is the starting value. The step-2 PR measures that overhead on the CI runner (a guard run on `ls`, start to exit, 20 runs) and records the worst run in the test; the test fails when the margin is under 3× that number.
- When the deadline expires, the guard denies, naming the step that was running. A hook killed at its timeout loses its denial, so the guard must stop itself first.
- **One backstop alarm stays.** `run_hook` arms a single `signal.setitimer(ITIMER_REAL)` at the alarm, the last resort that turns a check stuck outside a cooperative deadline check (a regex, a blocking read) into a denial. Its handler raises `hook_runtime.DeadlineExceeded`, a `BaseException` subclass, not an `Exception`, so a detector's `except Exception` (merge-guard has such blocks today) cannot swallow it; `run_hook`'s `BaseException` catch turns it into the deny, naming the step that was running. The cooperative `Deadline.check()` raises the same class. `setitimer` exists only on POSIX and works only on the main thread. A hook runs as its own process on the main thread, so the only place it is missing is Windows, where the cooperative deadline is the only stop. `run_hook` checks `hasattr(signal, "setitimer")` and `threading.current_thread() is threading.main_thread()` and says so in its docstring; the alarm test is skipped on Windows.
- `check-review-gate.gh_deadline` is not touched. It runs in CI, not as a hook, and is installed standalone.

### Parity corpus: the gate for retiring a legacy detector

The corpus is a list of exact command strings, each with its `tool_name` where the row has one, kept per skill: `pr-merge-flow/tests/fixtures/pr_guard_inputs.txt` (the #127 corpus, extended) and a new `review-gate/tests/fixtures/merge_guard_corpus.txt`. It holds: (1) every command in every deny test of that guard's existing suites; (2) every command in every row and allow row of the table above, spelled exactly; (3) the four round-3 probes of section 0, each as the exact command and payload. A corpus line is never edited or dropped to make a test pass; removing one needs a stated reason in the PR.

Two tests use it:

- **Release differential (phase 1 and after).** The baseline guard from the previous release's tag runs against the head guard over the corpus (the #127 harness mechanism): every command the baseline denies, head denies. This is the phase-1 invariant (section 0) as a test, and it runs in CI on every PR that touches a guard.
- **Coverage differential (the phase-2 gate).** For each legacy detector family that a phase-2 PR retires, `token_checks` alone denies every corpus command that family's detectors denied (each guard exposes `legacy_checks` and `token_checks` separately for this). The test names the family and fails listing each command the tokenizer misses. A family goes in the PR that makes this pass for it, and not before.

## Not in scope

- The guard stays a best-effort client-side check, not a security boundary. The server-side boundary is plan `2026-11-17-api-merge-guard.md`.
- **pr-guard's `Bash`-only tool policy.** pr-guard ignores a payload whose `tool_name` is not `Bash`; merge-guard checks any payload with a command. This plan keeps each guard's policy as it is, so it adds no allow and no unreviewed denial. Aligning them is a separate change with its own review.
- Effects the command text does not show: a git hook, an editor or a script file that runs a merge (`GIT_EDITOR=./merge.sh git commit` with no merge text). The guard cannot read those files' behavior; the server-side plan covers them.
- Variables, `eval` of computed text and command substitution in the command position are not evaluated. They deny when the words or fragments show a merge (R2, R4, R5 and R6 in both guards; R3 in merge-guard). A command name computed at run time with no `merge` word or fragment (`$(printf 'gh pr m%s' erge) 7`) is allowed, today and after this plan: the known limit in section 2.
- No Bash re-implementation beyond word formation. The tokenizer does no expansion it cannot do from the text alone.
- **The forged-check scripts.** `check-forged-gate-names.py` is vendored byte-identical from aec, and `check-forged-review-gate.py` is a thin wrapper around it, so typed JSON parsing for them (parse each API record once into typed fields, a verdict enum instead of `re.search(r"is also (PR #|open)", why)` over its own message, fail closed on a missing or malformed field) belongs in an aec-owned plan. It was routed to aec's owner through the aec traffic cop on 2026-11-21. claude-skills re-vendors the result.
